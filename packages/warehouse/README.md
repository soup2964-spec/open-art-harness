# @openart-signal/warehouse

A dbt project that turns OpenArt's raw sources (Stripe, Amplitude, the credit ledger, stored
click ids, HubSpot) into:

- a **conversion ledger** that conforms to the `ConversionLedgerEvent` contract;
- **serving cost** per generation;
- a **purchase value score** for ad platforms: `E[gross profit over 90 days | purchase]`, scored
  at the purchase (`PurchaseValueScore` contract);
- a **24-hour score** for experiment readouts: unconditional `E[90-day profit per exposed user]`
  (`PredictedProfit` contract), never an ad value;
- a **profit-per-arm readout** of the default-model experiment, plus the per-day × segment × slice
  mart the bandit-allocator reads;
- **audience candidates**;
- a **reconciliation** of Stripe against what each ad platform reports;
- a **data-quality quarantine** and **append-only score logs** with the fitted parameters behind
  every score.

It targets **BigQuery** in production (the JD's warehouse, with Metabase on top) and runs locally
on **DuckDB** against the `packages/contracts` fixtures. One set of model files compiles on both.
The SQL that differs between engines (JSON extraction, SHA-256 hex, safe division, epoch and
time-zone functions, JSON aggregation, quantiles, first-by aggregates) lives in adapter-dispatched
macros in `macros/cross_db/`.

> **Data provenance.** Locally, everything is synthetic. The contracts cohort is 2,000 generated
> users in OpenArt's real source shapes. The platform-side reports and invoice-lookup log are
> generated by `scripts/make_platform_reports.py` and labelled `synthetic` on every row; five
> scenario-user rows (`fixtures/scenario_users/`) are synthetic too. No OpenArt or ad-platform
> data is used, and nothing is sent anywhere.

## Quickstart

```bash
cd packages/warehouse
scripts/build.sh                  # everything below, then the offline BigQuery compile check
scripts/build.sh --skip-bigquery  # same, without step 7
```

`build.sh` runs seven steps; each one also works on its own:

| Step | Command | What it does |
|---|---|---|
| 1 | `uv run scripts/make_platform_reports.py --check` | Confirms the SYNTHETIC platform fixtures are current (deterministic regeneration). |
| 2 | `uv run scripts/load_fixtures.py` | Loads the fixtures into DuckDB raw schemas that mirror the BigQuery raw tables (and drops the previous build, so the append-only logs start empty). |
| 3 | `scripts/dbt.sh build --target local` | Seeds, models, data tests and unit tests; then re-runs the three append-only logs to prove a second run adds nothing. |
| 4 | `uv run scripts/export_contract_rows.py` | Writes contract-shaped JSONL for the TypeScript validators (ledger, both scores, exposures, the bandit's daily rows, per-user segments, audiences). |
| 5 | `uv run --with pytest ... pytest python_tests` | Plumbing check vs the cohort ground truth, the out-of-time backtest, docs SQL, week-1 queries on the fixtures, raw layer, fixtures, parameters, metric helpers. |
| 6 | `npx vitest run` | Every exported row checked with the contracts' own zod and ajv validators; the bandit's own zod schema and segment functions; golden rows; seeds. |
| 7 | `scripts/check_bigquery_compile.sh` | The `prod` profile parses; every model and test compiles with dbt-bigquery (incremental branch pinned) and parses as BigQuery. |

**Toolchain.** `uv` resolves Python 3.11+ with dbt-core 1.12.5, dbt-duckdb 1.11.0, duckdb 1.5.6
and, for step 7, dbt-bigquery 1.12.1. Node packages come from the repo root, so there is no
`npm install`. There are no dbt packages, so nothing runs `dbt deps`. Telemetry is off.

## The two scores, and why there are two

| | `fct_purchase_value_score` | `fct_predicted_profit_24h` |
|---|---|---|
| Estimand | `E[gross_profit_90d \| purchase]` | unconditional `E[90d profit per exposed user]` |
| Anchor | the purchase | signup + 24h |
| Unit | purchase event (`purchase_<invoiceId>`) | user |
| Used by | ad platforms (conversion-service value), audiences | experiment readout, bandit reward |
| Never used for | readouts (it conditions on buying) | ad values (a day-9 purchase would get p × value) |

Both are transparent structural estimators with every coefficient in `dbt_project.yml` and every
FITTED value in `dim_model_parameters`, and both are **cross-fitted**: a user in fold `k`
(`cf_fold`, from the uid's SHA-256) is scored with parameters fit on the other folds (`fit_id xf<k>`),
so no score uses its own outcome. `assert_backtest_never_trains_on_its_test_week` proves it.

**Purchase value score.** Renewal survival `s = P(renew within 45 days | tier, country bucket)`
(two-level EB, learnt from every observable renewal decision), expected renewals `s + s²`, add-on
revenue per paid month, the subscriber's own paid burn blended with plan utilisation × plan credits,
the user's own pre-purchase $/credit blended with the MEASURED $/credit of their default-model arms,
payment / affiliate / dispute fees and refund + chargeback rates. The interval is the 10th–90th
percentile of the model's own outcome distribution (0/1/2 renewals × burn ± CV). Features are
only what was known at the purchase (`assert_features_known_before_anchor`).

**24h score.** Segment conversion rate (paid / not activated / activated / trial depleted), converter
value, MEASURED $/credit per arm and measured paid-video credit share, all EB-shrunk towards
ILLUSTRATIVE priors. Signals-only by default (`pp_use_arm_calibration: false`). The arm terms
(`predicted_profit_with_arm_terms`) are cross-fitted and shrunk by the between-arm variance beyond
noise (`tau2`): when the arms differ no more than noise explains they are exactly 1. On the fixture
they are, for every image arm.

**Swap-in.** `--vars '{predicted_profit_source: external_scores}'` reads a trained model's 24h
scores from `ml.predicted_profit_scores` (same contract columns); readouts use them unchanged.
`fct_user_features_24h` and `int_pvs__features` are the training tables.

## Accuracy: an out-of-time backtest on SYNTHETIC data

There is no in-sample accuracy number. `target/accuracy_report.md` is a PLUMBING check: the
warehouse's realised arm and purchase economics equal an independent Python computation from the
raw fixture files (`python_tests/truth.py`) to the cent. Skill is measured out of time
(`python_tests/oot_eval.py`, `target/oot_backtest_report.md`): for each of the last three complete
signup weeks the parameters are fit on earlier signups only, the week's users and purchases are
scored, and the scores are compared with their realised 90 days. All numbers below are from the
synthetic generator and say nothing about OpenArt's users (see `docs/VALIDATION_PLAN.md`).

Purchase value score, 24 matured out-of-time purchases: calibration slope 1.08 (95% CI 1.00–1.09),
intercept −$13.5 (−21.5 to −3.9), top-decile lift 6.0, capped MAE $10.9 (6.3–16.1) against $20.0
(12.7–28.4) for the first-charge-revenue baseline and $228 for a flat mean; 79% of realised outcomes
fall inside the 80% interval. Per kind: annual slope 1.09, monthly 1.15 (0.55–1.38), packs 0.27 on
4 purchases. Small n: this is a shape check, not a claim.

24h score, 707 out-of-time users: calibration slope 0.67 (0.19–1.28), top-decile lift 1.05
(0.05–3.95), capped MAE $14.3 vs $21.6 for a conversion-only predictor; the decile table is flat
across the bottom half (predicted $0.4–0.9, realised $0) and noisy at the top. The arm-term
variant is worse (slope 0.13). It is a weak per-user predictor, which is why it is used only as an
arm-level readout with model-error intervals: over 21 (week, flag, arm) cells the interval with the
cross-fitted residual variance covers the realised arm mean in 100% of cells; the old
sampling-only interval covered 5%.

## The experiment readout and the bandit-allocator's mart

`fct_experiment_profit_by_arm` (one row per flag × arm) and `fct_experiment_profit_by_arm_daily`
share `int_experiment__user_readout`:

- **Intention to treat.** The arm is the first-exposed arm; users who later saw another arm are
  kept and counted (`contaminated_users`). Every non-QA exposure is a row member, scored or not.
- **Matured, fixed horizon.** Realised outcomes cover `[first exposure, + 90 days)` for users whose
  horizon is complete (`matured_users`); nothing is truncated at the as-of, so growing arms are not
  under-counted.
- **Uncertainty.** `predicted_profit_ci_*` adds the cross-fitted model-error variance to the
  sampling variance (the flag's pooled residuals below `readout_min_matured_for_arm_error` matured
  users); `predicted_profit_stratified_*` post-stratifies on paid-within-24h; `ppi_profit_*` is the
  bias-corrected prediction-powered estimate with `ppi_bootstrap_ci_*` from a deterministic Poisson
  bootstrap (`readout_bootstrap_replicates`; 200 on fixtures, off in prod by default);
  `predicted_profit_sampling_ci_*` is the old interval, kept only so the allocator's readout adapter
  can recover sufficient statistics.
- **Variance reduction.** `predicted_profit = mean_p_convert × value_if_converted_usd − unconditional_cost_per_exposed_usd`;
  pooling `value_if_converted_usd` over arms gives a lower-variance reward. `cuped_covariate` is a
  cross-fitted pre-exposure segment value; `realised_profit_cuped_per_exposed_usd` and `cuped_theta`
  show the adjustment.

`fct_experiment_profit_by_arm_daily` columns, for `packages/bandit-allocator`:

## Reproducibility: parameter snapshots and score logs

`int_model_parameters__current` lists every var (OBSERVED / ILLUSTRATIVE / CONFIG) and every FITTED
value of the serving fits (`xf<k>` and `all`) for both scores; `fitted_params_ref` is
`dim_model_parameters@<sha256 of name=value pairs>`. `dim_model_parameters` is append-only (a run
inserts its set only when the ref is new; `full_refresh` is disabled). Every score carries the ref
and `run_id` (dbt's invocation id); `fct_purchase_value_score_log` and `fct_predicted_profit_24h_log`
append the first score of each purchase / user per model version.
`assert_score_logs_are_reproducible` checks that every logged ref exists and that logged values under
the current ref equal the current scores. `build.sh` runs the logs twice to prove a second run
adds nothing.

## Point in time

Every feature is bounded by its anchor, and every fact used carries its timestamp
(`*_at`, `*_known_at`); `tests/singular/assert_features_known_before_anchor.sql` fails on any
timestamp after the anchor (24h features: `< signup + 24h`; purchase features: `<= occurred_at`).
Click ids and UTMs keep every value with `known_at` (the store's `received_at`), so a re-click after
a purchase cannot hide the click before it; the acquisition channel, which drives the affiliate fee,
is computed per anchor by `macros/openart/acquisition.sql`. Country and device come with the time
Amplitude first recorded them. Unit tests cover each bound (`ledger_attribution_is_what_was_known_at_event_time`,
`features_24h_only_use_what_was_known_before_the_window_end`, `acquisition_prefers_the_store_per_key...`).

## Money

Stripe amounts are minor units of the charge currency and include tax. `int_stripe__purchases`
derives `revenue_minor` (tax-exclusive, from `total_excluding_tax`) and converts both to
`var reporting_currency` at the rate valid on the purchase date (`int_fx__rates`, from
`seeds/fx_rates.csv` and `seeds/currency_minor_units.csv`). The seeded rates are ILLUSTRATIVE
placeholders: replace the seed with a daily reference-rate feed before trusting non-USD revenue.
A currency without a rate is never converted at 1.0: the purchase is quarantined and not scored.
The ledger keeps `cash_value_minor` (the contract) and adds `cash_value_reporting` and
`revenue_reporting`; profit models use the latter.

## Data quality and error handling

No data problem stops the build. Error-severity gates apply only to structural invariants
(uniqueness, contract formats, the net-cash identity); everything else is warn-level and lands in
`fct_data_quality_quarantine` with a `severity` (`excluded` = kept out of the ledger / scores,
`flagged` = used but needs a look) and a `ledger_cash_difference_minor`, so
`assert_ledger_net_cash_matches_stripe` proves ledger net = Stripe net + explained differences to
the cent. Alert on the `rpt_data_quality` view.

## Dropping it into OpenArt's BigQuery

**1. Datasets it creates.** dbt names datasets `<OPENART_BQ_DATASET>_<layer>`:
`openart_signal_staging`, `openart_signal_intermediate`, `openart_signal_marts`,
`openart_signal_reporting` and `openart_signal_seeds`. Marts are partitioned by event day and
clustered; `stg_amplitude__events` is incremental (`insert_overwrite` by `event_time` day, a
3-day `server_upload_time` lookback, `require_partition_filter`: every reader states its history
bound, `amplitude_history_start`). Metabase needs only `openart_signal_reporting`.

**2. Point the sources at what already exists.** Set the vars; no model changes.

| Source | Likely already in BigQuery | Var(s) | If it is missing |
|---|---|---|---|
| Amplitude export | Probably: Amplitude and BigQuery are both in the JD stack. Table `EVENTS_<project_id>`. | `raw_amplitude_schema`, `raw_amplitude_events_table` | Enable Amplitude's BigQuery destination (hourly), or land the Export API into the documented columns. |
| Stripe | Possibly via Stripe Data Pipeline (tables, 3-hour refresh). | `raw_stripe_schema`, `raw_stripe_events_table` | Add a webhook endpoint (Cloud Run) or forward OpenArt's existing handler through Pub/Sub into a BigQuery subscription table with Event columns (`id, type, created, api_version, livemode, data, received_at`). |
| Credit ledger | Unknown (per-user API only; Firestore is likely [I]). | `raw_app_schema` | Firestore → BigQuery streaming extension, CDC or a nightly export, keeping the API entry shape. |
| Click-id store, users | Unknown (backend tables behind `/api/user/ad-click-ids`, `my-info`). | `raw_app_schema` | Replicate those tables. |
| HubSpot | Unknown. | `raw_hubspot_schema` | CRM connector or webhooks with the same fields. |
| Platform reports | Probably Google Ads and Facebook Ads through BigQuery Data Transfer Service. | `raw_platforms_schema` | Per-platform staging views that map DTS tables onto `daily_conversions` (platform, account, layer, report date, conversions, value). |
| Allocation log | No. | `allocation_log_relation` | The bandit-allocator appends its applied weights (flag, arm, slice, valid_from, valid_to, assignment_probability). Without it the readouts carry NULL propensities. |

webhook sink, which Meta's 1-hour window needs anyway. With Stripe Data Pipeline instead,
replace each `stg_stripe__*` model with a thin view over the matching table and keep the same
output columns. Downstream nothing changes.

|---|---|
| `stg_stripe__invoices` | `invoices` (incl. `total_excluding_tax`) |
| `stg_stripe__invoice_lines` | `invoice_line_items` (line periods drive subscription status) |
| `stg_stripe__invoice_payments` | invoice payments, or `charges.invoice` on pre-basil versions |
| `stg_stripe__checkout_sessions` | `checkout_sessions` |
| `stg_stripe__refunds` | `refunds` (already one row per refund; `refund_step_minor` = `amount`) |
| `stg_stripe__disputes` | `disputes` (status carries the lifecycle) |
| `stg_stripe__subscription_events` / `_items` | `subscriptions` / `subscription_items` snapshots |

- **Service account.** Needs BigQuery Data Viewer on the raw datasets, Data Editor on the five
  `openart_signal_*` datasets, and Job User.
- **Scheduling.** A Cloud Run Job or Composer task after the sources refresh (hourly works).
- **As-of instant.** In prod it is `CURRENT_TIMESTAMP`; pin it with `--vars '{as_of_timestamp: ...}'`
  for backfills. Every staging model ignores source rows received after the as-of, so a pinned
  backfill sees exactly what the warehouse knew then.
- **Synthetic parts.** `fixture_mode` is off outside the `local` target, so ground-truth tests
  and synthetic sources are disabled automatically.
- **Append-only logs** (`dim_model_parameters`, `*_log`) have `full_refresh: false`; a `--full-refresh`
  leaves them alone.

**5. The BigQuery SQL is checked offline.** `scripts/check_bigquery_compile.sh` parses the
project with the real `prod` profile, compiles every model and data test with dbt-bigquery (the
incremental branch pinned with `compile_check_force_incremental`, the bootstrap SQL switched on),
and parses the compiled files with sqlglot's BigQuery dialect. It uses a dummy token behind a
dead proxy, so no request can leave the machine. It is a syntax check, not a dry run.

## Reconciliation

`fct_reconciliation` rebuilds, one behaviour at a time, what each platform reports from the
ledger (rules in `seeds/platform_reporting_rules.csv`, from research/02 §3.2 and research/11 §3).
Each step is a cause:

- **Money and scope.** `refunds_not_netted`; `out_of_scope_purchase_types` (renewals, upgrades,
  add-ons and packs; Meta/TikTok count the first purchase only); `blocked_users` (blocker proxy).
- **Counting and value.** `double_counting` (two Google accounts; X's twin `gtm_purchase`);
  `ltv_in_value` (Meta/TikTok); `value_not_sent` (LinkedIn); `fallback_misvaluation` (failed invoice lookup).
- **Reporting.** `time_zone`; attributed layer only: `unattributed_users`, `attribution_window`,
  `click_vs_conversion_date`.

`stripe_truth + Σ steps = platform_reported` holds by construction at full precision (round in
BI), and `residual` is what the causes do not explain. The Stripe truth path is independent of the
ledger (its own FX lookup, distinct payment intents, its own dispute netting). On the SYNTHETIC
reports the residual is 0 for every month, platform and layer: the reports come from an
independent Python implementation of the same rules (`make_platform_reports.py`). In production
the reports come from the platforms, and a non-zero residual is the finding.

## Parameters and labels

Every number that is an assumption is a var marked ILLUSTRATIVE in `dbt_project.yml` and in
`dim_model_parameters`: estimator priors and shrinkage strengths, retention, utilisation, video
credit share, refund and chargeback probabilities, the purchase value score's priors, payment
fees, dispute fee, vendor discount, failed-generation billing, audience thresholds, attribution
clock skew, the CUPED and readout settings. OBSERVED values are cited next to the var (Tolt 20%
commission, median list $/credit, cheapest default image arm, plan prices and credits, the stale
fallback price table, default-model arms). FITTED values are listed per fit with their sample
sizes. In `seeds/platform_reporting_rules.csv`, account time zones and non-Google/Meta
attribution windows are ILLUSTRATIVE; `seeds/fx_rates.csv` is ILLUSTRATIVE throughout.

## Safety and privacy

- Local only; no credentials in files (prod uses ADC; the compile check uses a dummy token); dbt
  telemetry off; no dbt packages.
- Personal data stays in raw: the Stripe staging whitelists object fields (no email, name,
  address, billing details, hosted URLs), Amplitude keeps typed extracts only (no raw property
  JSON), the click-id store keeps no landing URL or referrer, HubSpot keeps the page path only.
- BI reads aggregate-only views; the marts' identifier columns are for the services and should
  carry policy tags (`docs/metabase/DASHBOARDS.md`).
- Audiences materialise no hashed identifier; audience-sync hashes per platform at upload, and
  uploads are gated by the contracts' `CONSENT_REQUIRED_REGIONS` (unknown region fails closed).
- Every fixture value is synthetic: uids start `Synth`, emails use `.test`.
